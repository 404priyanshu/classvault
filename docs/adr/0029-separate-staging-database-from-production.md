# Separate the Staging Database from Production

ClassVault runs local development and every hosted pgTAP suite against a dedicated staging Supabase project, not against the production project that serves real students. Production stays reachable only through `npm run db:push:production` with the production ref explicitly linked, so a migration reaches live data as a deliberate, separately reviewed act rather than as a side effect of working on a laptop. We accept the cost of a second hosted project, a second set of Auth/SMTP/Turnstile settings that no migration can carry, and the drift risk between two dashboards, because the previous arrangement gave every `db push`, `db reset`, and transactional test suite write access to live student uploads, memberships, and rooms — a class of accident no amount of care at the keyboard reliably prevents. The guard lives in `scripts/supabase-target.mjs` and `scripts/run-pgtap-hosted.py` and fails closed: an unlinked or production-linked project stops the command, and the override is an environment variable a person has to type.
