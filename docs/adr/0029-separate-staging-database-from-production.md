# Separate the Staging Database from Production

ClassVault runs local development and every hosted pgTAP suite against a dedicated staging Supabase project, not against the production project that serves real students. Production stays reachable only through `npm run db:push:production` with the production ref explicitly linked, so a migration reaches live data as a deliberate, separately reviewed act rather than as a side effect of working on a laptop. We accept the cost of a second hosted project, a second set of Auth/SMTP/Turnstile settings that no migration can carry, and the drift risk between two dashboards, because the previous arrangement gave every `db push`, `db reset`, and transactional test suite write access to live student uploads, memberships, and rooms — a class of accident no amount of care at the keyboard reliably prevents. The guard lives in `scripts/supabase-target.mjs` and `scripts/run-pgtap-hosted.py` and fails closed: an unlinked or production-linked project stops the command, and the override is an environment variable a person has to type.

**Amended 2026-09-22.** The decision stands — development and tests never run against the production database — but the mechanism changed before the hosted staging project was ever created. The Supabase organization is on the Free plan, whose two-active-project limit was already taken, so isolation comes from a local Supabase stack in Docker instead: `npm run local:bootstrap` starts it, resets it to the repository's migrations, runs every pgTAP suite with `supabase test db`, and writes `.env.local` from its own status output. This trades away some of the costs above rather than accepting them: there is no second dashboard to drift and nothing to pay for, but hosted-only behaviour — custom SMTP, Turnstile, OAuth providers, and dashboard settings no migration carries — is not exercised before production, and each developer needs Docker. The fail-closed guard is unchanged and still applies whenever a hosted project is linked. `docs/staging.md` remains the runbook if a hosted staging project is created later, for example to give Vercel Preview deployments a database of their own.
